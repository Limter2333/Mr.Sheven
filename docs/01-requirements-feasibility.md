# 需求与可行性分析

## 原始需求

酒类测评博主对每款酒做评测，但用户记不住评测结论。希望：在商超购酒时拿出手机拍一下，
App 识别这款酒是否被指定博主评测过、打了什么分。系统内酒的数据靠后台程序对 B 站视频
自动总结并入库。

## 系统拆解（三个子系统）

1. **数据管道**：B 站视频 → 转写 → LLM 结构化抽取 → 人工审核 → 数据库
2. **识别匹配**：扫码（条形码）→ 匹配数据库记录（MVP 不做 OCR，全部依赖条形码识别）
3. **客户端**：手机拍照入口 + 结果展示

## 可行性结论

| 子系统 | 可行性 | 说明 |
|---|---|---|
| 数据管道 | 高 | ASR + LLM 抽取技术成熟，成本极低（单视频几毛~1元）；需人工审核兜底 |
| 识别匹配 | 高 | MVP 仅扫码（条形码），技术成熟可靠；被"垂类 + 已知酒单"决策降级为闭集匹配（见 02）；OCR 识别留 V2 再做 |
| 客户端 | 高 | 原生 App（Flutter 跨平台）；ICP 备案、App 备案、软著从 Phase 0 并行启动，避开串行等待（裁决 C2，见 06 文档） |

## 关键风险（按致命程度排序）

1. **命中率**（商业可行性瓶颈）：单博主评过的酒几百款 vs 商超 2000+ SKU，随机拍大概率查无此酒。
   缓解：聚焦垂类、聚合多博主、把"查不到"做成缺漏提交通道反哺抓取优先级。
2. **SKU 级消歧**：同款酒不同年份/度数/包装。对策：匹配结果 = 候选列表 + 置信度，低置信度让用户点选。
3. ~~实拍环境~~：MVP 仅扫码，不涉及 OCR 实拍问题（裁决 C9）。
4. **博主不打数字分**：很多博主只说"值/不值"。Schema 设计为"倾向 + 原话摘录"，不强依赖分数。
5. **法律合规**：
   - 爬 B 站处于 ToS 灰色地带：个人低频低风险，公开产品需谨慎；
   - 存"某博主给某酒打 X 分"的**事实性信息**并注明出处风险较低，禁止逐字搬运完整文案；
   - 公开 App 需 ICP 备案 + App 备案 → 原生 App（Flutter）+ 备案从 Phase 0 并行启动（裁决 C2，见 06 文档）。

## 数据端环节风险明细

| 环节 | 方案 | 风险 |
|---|---|---|
| 视频列表 | B 站接口 + bilibili-api-python / yt-dlp | 风控（wbi 签名、频率限制）、接口变动 |
| 获取文案 | B 站 AI 字幕优先；无字幕则**直接跳过**，不做 ASR 强攻（裁决 C8） | 依赖平台 AI 字幕覆盖率 |
| 结构化抽取 | LLM 输出 JSON | 一视频多酒需拆分；防幻觉需 quote 锚定 |
| 质量保障 | 人工审核队列 | 审核通过才对外可见 |

## 验证策略：探针实验

写任何管道代码前，先做低成本验证实验：

- **数据端**：9 个视频（2 博主 × 3 品类：红酒、威士忌、金酒）走通"转写 → 抽取 → 核对"，量化质量指标（裁决 C7：三个品类全做）；
- **识别端**：MVP 仅扫码（条形码），不做 OCR 探针（裁决 C9）。P0 阶段做 100 个进口酒条码的第三方 API 覆盖率抽样测试（裁决 C10）。

任一实验不通过只损失一天；通过则技术选型有数据支撑。详见 03 文档。
