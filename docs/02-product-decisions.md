# 产品决策记录

## 已确定的决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | **聚合多个博主**，不做单一博主 | 扩大酒款覆盖面，直接缓解命中率问题 |
| D2 | **垂类先行**：红酒、金酒、威士忌（三品类全做） | 博主覆盖率与货架重合度更高；MVP 仅扫码（条形码），不依赖 OCR，故红酒不再需要"放二期"（裁决 C7） |
| D3 | **闭集匹配** | 数据库只有博主评过的酒（如 3 品类 × 200 款 = 600 候选），识别从"认出世界上任意一瓶酒"降级为"和 600 个已知候选匹配"，难度降一个数量级 |
| D4 | **分博主展示评分，不算平均分** | 保留信息量；"注明出处"更自然，版权上更干净 |
| D5 | **评分双层设计** | 原始层：博主原话 + 原始评分（含文字倾向）；归一层：统一三档（推荐/中性/避雷），映射规则每博主单独配置 |
| D6 | **实体对齐用"酒款主数据 + 别名表"** | 多博主写法不一（"麦卡伦12年双桶"/"Macallan 12 Double Cask"），匹配先过别名归一化；相当于电商 SPU/SKU 问题，是长期打磨重点 |
| D7 | ~~微信小程序/H5~~ → **原生 App（Flutter 跨平台）** | ~~原决策避开备案负担~~ → 已确认原生 App；备案从 Phase 0 并行启动（ICP 2~4 周 + 软著 1~2 月 + App 备案 1~2 周），开发期间用 TestFlight/内测分发不受限制。决策变更理由：原生 App 体验更好、相机/扫码能力更强、Flutter 一套代码双端（裁决 C2，见 06 文档） |

## 品类识别难度

> MVP 仅扫码（条形码），以下 OCR 友好度仅供 V2 参考（裁决 C9）。

| 品类 | 标签文字密度 | OCR 友好度（V2 参考） | 备注 |
|---|---|---|---|
| 威士忌 | 高（产区/酒厂/年份/酒精度） | ★★★ | 条码覆盖好 |
| 金酒 | 中高 | ★★★ | 条码覆盖好 |
| 红酒 | 低（法国酒庄标常只有花体名） | ★ | 进口酒条码覆盖好，MVP 三品类全做（裁决 C7） |

## 闭集匹配的落地含义

- MVP 仅通过**条形码**匹配：扫码 → 查 barcode 表 → 关联 SPU → 返回评测结果（裁决 C9，不做 OCR）；
- 匹配输出 = 候选列表 + 置信度，低置信度让用户点选，不硬给唯一答案；
- V2 预留：可为库内每款酒预存标准标签图，增加 OCR 文本匹配 + 图像相似度双通道。

## 概念数据模型（先想清楚再建表）

- **酒款**：品类、品牌、名称、度数、容量、标准标签图、条码
- **博主**：平台、主页、打分体系及归一化规则
- **评测记录**：酒款 ↔ 博主 ↔ 视频；含原始评分、归一评分、倾向、原话摘录、视频链接、发布时间
  - 粒度 = "某博主在某期视频里对某酒的评价"，同一博主重评同款酒存多条
- **别名**：酒款 ↔ 别名文本（标注来源），别名表种子数据可来自 ASR 纠偏词表
