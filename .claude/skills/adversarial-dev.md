# 对抗性开发（实时执行）

开发 + 对抗性审查 + 修正循环，支持多需求顺序执行。

## 使用方式

```
/adversarial-dev "需求1; 需求2; 需求3"    # 多需求模式
/adversarial-dev "@requirements.txt"       # 从文件读取
```

## 项目配置

**在使用前，请根据你的项目修改以下配置：**

### 质量标准（第 91-94 行）
- 核心模块覆盖率: > 95%
- 服务层覆盖率: > 80%
- API 层覆盖率: > 75%

### 项目规范（第 85-100 行）
- 命名规范
- 提交规范
- 代码风格

## 执行流程

### 1. 解析需求

从参数获取需求列表：
- 分号分隔：`"需求1; 需求2; 需求3"`
- 文件读取：`"@requirements.txt"`（每行一个需求，# 开头为注释）

如果没有提供需求，提示用户输入。

### 2. 顺序处理每个需求

对每个需求依次执行：

#### 阶段 1: 实现
- 读取相关文件，理解上下文
- 分析现有代码模式，保持风格一致
- 编写实现代码
- 添加测试覆盖正常和异常路径
- 遵循项目规范

#### 阶段 2: 对抗性审查

并行运行两个攻击者：

**攻击者 1 - 代码逻辑**
- 边界情况处理
- 异常路径覆盖
- 返回值正确性
- 状态一致性

**攻击者 2 - 测试充分性**
- 测试覆盖率
- 边界测试
- 断言强度
- Mock 使用合理性

只报告真正的 bug，不报告风格问题。

#### 阶段 3: 修复

如果审查发现问题：
- 逐一修复
- 添加测试
- 确保问题已解决
- 运行测试验证修复

如果审查通过，跳过此阶段。

#### 阶段 4: 提交
- 暂存所有变更：`git add -A`
- 提交：`git commit -m "feat: <需求描述>"`
- 记录提交哈希

### 3. 生成执行报告

```

📊 执行报告
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

总需求数: X
成功: X
失败: X

详细结果:
1. ✅ 需求1
2. ✅ 需求2
3. ❌ 需求3 - 失败原因
```

## 实现要求

### 命名规范
- Python: snake_case
- TypeScript: PascalCase（组件）/ camelCase（工具函数）
- 测试文件: test_xxx.py / xxx.test.tsx

### 质量标准
- 核心模块覆盖率: > 95%
- 服务层覆盖率: > 80%
- API 层覆盖率: > 75%
- 所有公共函数必须有 type hints

### 提交规范
- feat: 新功能
- fix: 修复 bug
- refactor: 重构
- docs: 文档更新

## 错误处理

- 单个需求失败不影响后续需求继续执行
- 所有错误都会记录在执行报告中
- 失败后继续处理下一个需求
