# Self-Loop 增强版（实时执行）

支持多需求顺序执行，集成对抗性验证的自动迭代开发。

## 使用方式

```
/self-loop-adv                          # 自动发现模式
/self-loop-adv "需求1; 需求2; 需求3"    # 多需求模式
/self-loop-adv "@requirements.txt"      # 从文件读取
```

## 项目配置

**在使用前，请根据你的项目修改以下配置：**

### 测试命令
测试命令**不写死在本文件**。每次执行前先读取项目根目录的 `CLAUDE.md`，
以其中「测试命令」一节的说明为准。若该节仍是 TODO，则按以下顺序探测：

1. `package.json` 有 `scripts.test` → `npm test`
2. 存在 `pyproject.toml` / `pytest.ini` / `setup.cfg` / `tox.ini` → `python -m pytest -v --tb=short`
3. 存在 `tests/` 目录 → `python -m pytest tests/ -v --tb=short`
4. 存在 `Makefile` → `make test`

探测不到就跳过测试阶段，**不要执行注定失败的命令**。

### 覆盖率要求（第 40 行、61 行、88-90 行）
- 核心模块: > 95%
- 服务层: > 80%
- API 层: > 75%

### 项目规范（第 82-97 行）
- 命名规范
- 提交规范
- 代码风格

## 执行流程

### 1. 解析需求

如果提供了需求参数，按分号分割或从文件读取：
- 分号分隔：`"需求1; 需求2; 需求3"`
- 文件读取：`"@requirements.txt"`（每行一个需求，# 开头为注释）

如果没有提供需求，进入**自动发现模式**：
- 运行 `python scripts/discover.py`（如果存在）
- 读取 `memory/backlog.md`（如果存在）
- 按优先级排序：HIGH > MEDIUM > LOW

### 2. 顺序处理每个需求

对每个需求依次执行：

#### 阶段 1: 实现
- 读取相关文件，理解上下文
- 分析现有代码模式，保持风格一致
- 编写实现代码
- 添加测试覆盖正常和异常路径
- 遵循项目规范（PEP8, type hints, 严格模式）

#### 阶段 2: 测试
- 按上文「测试命令」的规则确定命令后运行
- 检查覆盖率是否 >= 80%（项目未配置覆盖率工具则跳过此项）
- 如果测试失败，尝试修复（最多 6 次）

#### 阶段 3: 对抗性审查
并行运行三个审查者：
1. **逻辑审查**：边界情况、异常路径、返回值正确性、状态一致性
2. **测试审查**：测试覆盖、边界测试、断言强度、Mock 使用
3. **安全审查**：输入验证、错误处理、资源泄漏、并发安全

如果审查发现问题，立即修复。

#### 阶段 4: 提交
- 暂存所有变更：`git add -A`
- 提交：`git commit -m "feat: <需求描述>"`
- 记录提交哈希

### 3. 最终验证

处理完所有需求后：
- 运行完整测试套件
- 检查覆盖率 >= 80%
- 确认所有变更已提交

### 4. 生成执行报告

```

📊 执行报告
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

失败: X

详细结果:
1. ✅ 需求1
2. ✅ 需求2
3. ❌ 需求3 - 失败原因
```

## 实现要求

### 命名规范
- Python: snake_case
- TypeScript: PascalCase（组件）/ camelCase（工具函数）
- 测试文件: test_xxx.py / xxx.test.tsx

### 质量标准
- 核心模块覆盖率: > 95%
- 服务层覆盖率: > 80%
- API 层覆盖率: > 75%
- 所有公共函数必须有 type hints

### 提交规范
- feat: 新功能
- fix: 修复 bug
- refactor: 重构
- docs: 文档更新

## 错误处理

- 单个需求失败不影响后续需求继续执行
- 测试失败会自动尝试修复（最多 6 次）
- 审查发现的问题会立即修复
- 所有错误都会记录在执行报告中

## 循环控制

| 限制 | 值 | 原因 |
|------|-----|------|
| 最大迭代次数 | 20 | 防止无限循环 |
| 总时长超时 | 60 分钟 | 尊重用户时间 |
| 循环内执行超时 | 30 分钟 | 单次循环时间限制 |
| 单个失败最大修复次数 | 6 | 超过则升级 |
| 连续失败限制 | 3 | 检测卡住状态 |
